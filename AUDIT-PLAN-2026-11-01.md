# Atlantic Home — аудит і план розвитку

Дата: 1 листопада 2026 року. Мета: надійне керування домашнім кліматом, читабельний інтерфейс, швидкий запуск і зрозумілий облік енергії.

## Межі перевірки

Переглянуто локальний код Next.js, маршрути API, авторизацію, Neon, фоновий збір, Tuya, тарифні обчислення, CSS, manifest і service worker. У браузері перевірено production екран входу та його фактичні стилі. Захищені екрани оцінено за кодом: у браузерній сесії аудитора немає авторизації. Команди на реальні прилади не надсилались. Секрети не читались.

`npm run lint` та `npm run build` проходять. Це не підтверджує працездатність фізичних пристроїв або продуктивність на телефоні. Lighthouse, польові Core Web Vitals, доступність усіх екранів і поточний аудит залежностей ще потребують окремих вимірювань. Збірка попереджає про зайвий package-lock.json у батьківській папці.

Локальний checkout містить незакомічені зміни попередніх робіт. Перед реалізацією потрібно звірити його з production/main та зафіксувати базову версію. Аудит не змінює поведінку застосунку.

## Підтверджені проблеми та ризики за кодом

### P0 — довіра до стану, сесій і команд

1. **Токен інтерактивного Cozytouch не поновлюється.** `lib/overkiz.ts`, `withOverkiz`: після `expiresAt` повертається `COZYTOUCH_SESSION_EXPIRED`. Окремий фоновий модуль refresh має, але не оновлює токен у браузерній сесії. Наслідок: збір може працювати, а керування вимагатиме повторного входу. Зробити спільний серверний менеджер токенів з блокуванням одночасного refresh; у cookie залишити ідентифікатор сесії та доступ до застосунку.

2. **Відсутні покази можуть стати нулями.** `app/dashboard.tsx`: `Number(null)` для температури кімнати та накопиченого лічильника дає 0. Перевіряти null/undefined до числового перетворення; розділити значення, свіжість і помилку зчитування. Нуль дозволяти лише як реальний показ.

3. **Прийняття команди API виглядає як виконання.** Оптимістичне значення захищене лише 20 секунд; фактичний результат виконання не відстежується. Ввести стани «Надсилаємо», «Прийнято хмарою», «Підтверджено пристроєм», «Не підтверджено». Зіставляти результат виконання та наступні покази, коли API це дозволяє. Не повторювати команди автоматично після невизначеного тайм-ауту.

4. **Помилки змішуються з офлайном шлюзу.** Загальний catch опитування в dashboard прибирає liveDevice й виставляє gatewayOnline=false. Прострочена авторизація, помилка сервера та відсутність мережі отримують схожі повідомлення. Зробити окремі типи помилок і відповідні дії відновлення.

5. **Немає обмеження спроб входу.** У `/api/access/unlock` є безпечне порівняння пароля, але немає rate limit; мінімум пароля — лише 4 символи. Додати серверне обмеження частоти, поступові затримки та журнал невдалих входів без паролів. Не змінювати поточний пароль без дії власника; запропонувати сильнішу політику для наступної зміни.

6. **«Фоновий збір готовий» не доводить роботу cron.** `/api/cozytouch/background` перевіряє змінні й наявність токенів, але не останній запуск, помилку та успішне збереження. Додати таблицю запусків: start/end/status/error/device/sample timestamp. У UI окремо показати «Налаштовано» й «Останній успішний збір»; попереджати про пропуски.

7. **Спільний час виконання фонового збору може перевищити ліміт.** Є послідовні запити з тайм-аутами по 15 с, а cron route має maxDuration=60 і curl — 55 с. Це ризик за повільної хмари. Ввести загальний бюджет часу, повторне використання сесій, контроль конкурентності й обмежені повтори лише безпечних зчитувань.

### P1 — швидкість, енергія та збереження

8. **Повний вхід у Overkiz на кожне опитування.** JWT → login → setup повторюються раз на 30 с і для команд. На старті ConnectPanel, хоча схований, додатково запитує той самий state. У state також можливе повторне читання heater через список sensors. Зробити один координатор запитів на клієнті, унікальні deviceURL, короткий захищений серверний кеш setup/сесії на інсталяцію та окремий маршрут легкої телеметрії. In-memory кеш у serverless не вважати постійним сховищем.

9. **Опитування не враховує видимість і не захищене від накладання.** setInterval може почати наступне читання до закінчення попереднього; немає AbortController і backoff. Перейти на послідовний цикл після завершення попереднього запиту, паузу в прихованій вкладці та негайне читання при поверненні. Фоновий cron працює незалежно.

10. **Важкі дані повертаються при кожному читанні.** State містить definition, усі пристрої, сирі стани, діагностику та добові consumptions. Винести діагностику в запит за потреби; доступні команди кешувати; історію й добові підсумки читати повільніше та за потребою екрана.

11. **Часова зона тарифів залежить від браузера.** `energy-pricing.ts` використовує getHours/getDate, а не фіксовану зону житла. За кордоном одна історія може дати інший день/ніч і вартість. Використати IANA `Europe/Kyiv`, перевірити переходи літнього часу, межі місяця, 23:00 і 07:00. Тарифи залишити редагованими з датою початку дії; цей аудит не перевіряв актуальність законодавчих ставок.

12. **Пропуск показів виглядає як нульове споживання.** buildDailyEnergy заповнює відсутні дні нулями і рівномірно розносить дельту навіть через довгі паузи. Додати coverage, missing/estimated/measured, штрихування прогалин, окрему якість оцінки дня/ночі. Для початку періоду отримувати один попередній показ. Виявляти скидання лічильника та неправдоподібні стрибки.

13. **Підписи енергообліку суперечать логіці.** Один текст каже, що весь приріст потрапляє в день наступного зчитування, хоча алгоритм розподіляє його по часу. Домашня картка «сьогодні» може використовувати останню доступну добу Atlantic без перевірки дати. Ввести єдине джерело підсумків, показувати дату та походження значення.

14. **Хмарні налаштування можуть перезаписати нові редагування.** Пізній GET замінює локальний стан; автозбереження не має версій і захисту від переставлених відповідей. Додати revision/updatedAt, dirty state, послідовні записи та індикатор «Зберігаємо / Збережено / Помилка». Обгорнути всі звернення до localStorage в обробку помилок.

15. **Список пристроїв прив’язаний до energyHistoryId.** Без датчика енергії, доступного Cozytouch або налаштованої історії не активується незалежне збереження дому. Фоновий код бере перший energy sensor, керування — перший heater. Потрібні стабільний homeId та реальні providerDeviceId для кожного приладу; зв’язувати датчики з відповідним конвектором. Для майбутніх користувачів перевіряти володіння інсталяцією на сервері.

16. **Редаговані картки не є окремими підключеннями.** Можна додати кілька Mycond, але всі звертаються до одного TUYA_DEVICE_ID. Custom — лише запис у списку. Явно відрізняти «Підключений прилад» від «Запис у списку», не пропонувати дублікати без реальної прив’язки.

17. **Tuya UI виводить сирі значення.** Не застосовуються scale/unit зі специфікації, enum та boolean часто англійською, integer range не має локального onChange для плавного керування. Зробити адаптери підтверджених можливостей, українські назви, одиниці, локальний draft повзунка й перевірку відправленого результату. Реальна доступність Mycond потребує перевірки прив’язаного пристрою.

18. **Довгоживучі секрети мають неявний TTL.** saveBackgroundCredentials використовує sealData без ttl; встановлена iron-session за замовчуванням задає 14 днів. Регулярний refresh перепаковує payload, але тривала пауза може зробити запис нечитабельним. Визначити окрему політику зберігання/ротації ключа та строків фонових токенів; відрізняти їх від браузерної сесії.

19. **Схема БД створюється в runtime.** CREATE TABLE/INDEX виконується при першому зверненні нового процесу. Перенести схему у версійні міграції; додати агрегати день/місяць, політику збереження сирих показів, резервне копіювання та контроль розміру. Наразі API історії обмежений 32 днями.

### P1 — дизайн і PWA

20. **Три накладені CSS-шари.** globals.css, light-theme.css і design-system.css містять різні покоління стилів, повторені медіазапити, старі темні кольори й локальні override. На екрані входу фактично залишилися підписи 11 px та пояснення 12 px. Зелена темна пляма у фоні входу успадкована від старої теми. Попереднє збільшення шрифтів не охопило всі елементи.

21. **Недостатній контраст вторинного тексту.** #71879a на білому ≈3,73:1; #7891a7 ≈3,28:1; #7e92a4 ≈3,21:1. Для звичайного тексту орієнтир WCAG AA — 4,5:1. Розміри та кольори треба перевіряти на фактичному тлі кожного компонента, включно зі станами disabled/error.

22. **30 підписів дат стиснуті у вузький графік.** Підписи повернуті, nowrap, контейнер overflow:hidden; збільшення шрифту підсилює ризик перекриття/обрізання. Показувати 4–6 підписів осі, читати значення по торканню, додати доступну таблицю. Не ховати проблему загальним overflow-x:clip.

23. **Декоративний простір конкурує з керуванням.** Вітальний заголовок і велике коло температури займають значну частину першого екрана. Картки з постійно недоступними даними й технічні пояснення подовжують сторінку. Першим показати фактичну температуру, ціль, живлення, режим і свіжість; деталі відкривати окремо.

24. **Навігація зберігається лише в React state.** Reload завжди повертає на головну; Back і прямі посилання на вкладки не працюють як очікується. Ввести маршрути або URL-параметр, збереження scroll для екрана, aria-current для активного розділу та керування фокусом.

25. **PWA не має сценарію запуску без мережі.** SW не обробляє fetch, при activate видаляє всі Cache Storage ключі цього origin, відразу skipWaiting/claim. Реєстрація примусово reload на controllerchange. Потрібні версійні кеші лише цього застосунку, безпечна offline-сторінка, останній дозволений snapshot з часовою міткою та повідомлення про оновлення. Захищений HTML/API і команди не кешувати без окремої моделі доступу. При lock видаляти приватний локальний snapshot. Команди не ставити в offline-чергу.

26. **Manifest використовує лише SVG.** PNG 192/512 вже є у public, але не зазначені; немає maskable icon, стабільного id і shortcuts. Додати їх та перевірити встановлення в Safari iOS/Chrome Android.

27. **Заборонене масштабування.** Це попереднє побажання власника, тому не міняти мовчки. План: усунути випадкове масштабування полів через font-size≥16 і коректну верстку; погодити повернення користувацького zoom та додати режим збільшеного тексту. Повне блокування zoom погіршує доступність.

28. **Зовнішні шрифти через CSS @import.** Додають залежність від Google Fonts на старті, можливі затримки та заміна метрик. Перейти на один локально розміщений шрифт з українською кирилицею або системний стек; перевірити зсуви компонування.

## Запропонована структура і візуальна мова

Зберегти світлий інтерфейс і синій акцент. Використати нейтральний світлий фон, темний текст, один узгоджений набір іконок, мінімальні тіні та радіуси 16–20 px. Акцент залишити для активного керування; зелений/бурштиновий/червоний — для станів із текстовими підписами.

Основний текст 16 px, пояснення 14 px, другорядні мітки 12–13 px; 11 px лише за обґрунтованої потреби в графіку. Міжряддя 1,45–1,6; відступи за шкалою 4/8/12/16/24/32. Основні touch-кнопки 44–48 px. Один H1 на екран, передбачувані H2, читабельні focus і error стани. Підтримати український текст без надмірного uppercase.

Екрани:

- **Дім:** поточна температура кімнати та її свіжість, картка конвектора з ціллю/живленням/режимом, компактна енергія за сьогодні, підключений Mycond із вологістю. Замість привітання на пів екрана — коротка назва кімнати.
- **Розклад:** перемикач, тиждень, зрозумілі інтервали дня, режими комфорт/еко, копіювання дня. Raw JSON лише в діагностиці. Вимкнення розкладу не трактувати як вимкнення живлення.
- **Енергія:** сьогодні / 7 днів / місяць / довільний період; кВт·год і грн, якість даних, графік день/ніч, деталізація дня. Тарифи редагувати у висувній панелі. Стан збору — компактний рядок із деталями.
- **Пристрої:** реальні прилади, кімнати, підключення та можливості. Редагування в окремій формі, видалення з можливістю скасування. Прилад без інтеграції має чіткий відповідний статус.
- **Налаштування:** акаунти, тарифи, вигляд/розмір тексту, сповіщення, доступ, стан системи. Назва «Профіль» зараз неточна для такого вмісту.

На телефонах — одна колонка й нижня навігація; на планшеті/desktop — ширша сітка та бокова навігація, а не панель шириною максимум 560 px посеред екрана. Зберегти safe area, врахувати клавіатуру й горизонтальну орієнтацію.

## Нові функції та умови реалізації

### Варто додати першими

- Журнал команд і подій: що змінилося, звідки команда, чи підтверджена.
- Час останнього успішного зчитування, історія збоїв і автоматичне відновлення після появи мережі.
- Таймер тимчасового режиму: «До 22:00», «На 1 годину», повернення до попереднього режиму. Для серверного таймера потрібні стійке сховище й надійний виконавець.
- Обрані комфортні цілі та швидкі дії: «Вдома», «Відсутність», «Ніч». Доступні дії формувати з capability пристрою.
- Графік температури; для Mycond — вологості, якщо API її реально повертає. Разом з енергією видно вплив налаштувань.
- Порівняння днів і тижнів, бюджет у грн/кВт·год, прогноз за достатньої історії з позначкою оцінки.
- Експорт CSV за період, резервна копія налаштувань, історія тарифів з датами.

### Після стабілізації основи

- Редактор розкладу конвектора: спершу прочитати підтримувані команди/формат на конкретній моделі; round-trip перевірка, резервна копія програми, повернення попередньої. До цього доступні перегляд у людському вигляді та перемикач наявного PROG.
- Сповіщення про втрату зв’язку, перевищення бюджету, температуру/вологість поза межами, повний бак Mycond — тільки якщо відповідні дані доступні. Потрібні серверна оцінка правил, затримки, гістерезис, тихі години та згода на канал.
- Кілька кімнат/конвекторів із реальним вибором deviceURL. Сімейний доступ і passkeys — окремий етап моделі користувачів та дозволів.
- Темна тема та режим великого тексту після завершення базової системи стилів.

### Що не обіцяти без додаткових даних

- Миттєва потужність, струм і напруга не підтверджені наявними показами конвектора. Накопичений Wh дозволяє обчислити середню потужність за інтервал, але не поточні Вт чи Вольти. Середню позначати саме як середню. Для справжніх вимірів потрібен сумісний вимірювач із відповідними характеристиками.
- Номінальні 1000 Вт не дорівнюють фактичному поточному споживанню. Режим comfort не підтверджує, що ТЕН зараз гріє.
- Додавання картки Mycond не підтверджує інтеграцію. Перед функціями керування треба перевірити прив’язку акаунта, специфікацію та реальні команди.
- Частіший cron не усуває затримку оновлення самого лічильника Cozytouch.

| Етап | Обсяг | Критерій готовності |
|---|---|---|
| 0. Базова версія | Звірити production і checkout, зафіксувати сценарії та виміри | Відомий commit, відтворюваний build, зафіксований стан до змін |
| 1. Надійність | Єдиний refresh, правильні null/статуси, підтвердження команд, rate limit, heartbeat збору | Закінчення токена не вимагає пароля; немає фальшивих нулів/офлайнів; видно реальний збір |
| 2. Швидкість | Прибрати дублікати, кероване опитування, легка телеметрія, кеш setup, діагностика окремо | Один запит стану на старті; немає накладання; прихована вкладка не опитує; збій хмари не блокує оболонку |
| 3. Дані | homeId/deviceId, міграції, таймзона, coverage, тарифні періоди, синхронізація версій | Однакові підсумки на різних пристроях; пропуски не нулі; немає втрати редагувань |
| 4. Дизайн | Один CSS/design system, нова ієрархія екранів, графіки, адаптивність | 320–1440 px без обрізання; читабельний текст; однакові компоненти; клавіатурна навігація |
| 5. PWA | Offline fallback, manifest, іконки, безпечні оновлення, очищення приватного snapshot при lock | Встановлення на iOS/Android; зрозумілий offline; нова версія не перериває введення/команду |
| 6. Функції | Журнал, історія клімату, таймери, бюджети, потім редактор програм і сповіщення | Кожна функція спирається на перевірені можливості та має сценарій помилки/відновлення |

Етапи 1–3 варто завершити до масового додавання автоматизацій. Візуальну систему можна розробляти паралельно з виправленнями, але випускати невеликими перевіреними змінами. Оцінку строків давати після звірення production і перевірки реальних provider-команд.

## Перевірки перед випуском

- Сценарії: lock → unlock, некоректний пароль, втрата cookie, прострочений токен, відкликання refresh, відсутність Neon, тайм-аут хмари, офлайн шлюз, порожні покази, повернення мережі, два відкриті браузери.
- Команди: відхилення, прийняття без виконання, повільне підтвердження, повернення фактичного значення; реальні команди лише в погоджений момент, без випадкового керування під час аудиту.
- Енергія: 0/null, скидання лічильника, довга пауза, початок періоду, місяць/рік, перехід часу, 23:00/07:00, 2000 і понад 2000 кВт·год; тестувати задані власником правила окремо від перевірки правових тарифів.
- UI: 320/360/390/430/768/1280/1440 px, текст 200%, клавіатура, VoiceOver, safe area; Safari iOS, Chrome Android, desktop. Графік має альтернативну таблицю.
- Цільові Core Web Vitals після вимірювання: LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1 на 75-му перцентилі. Це цілі, не поточні результати. Відокремити час запуску UI від часу відповіді Cozytouch.
- CI: npm ci замість npm install, lint, TypeScript/build, тести критичних тарифних/авторизаційних сценаріїв, контроль залежностей. Не приймати факт успішного build як доказ end-to-end роботи.
- GitHub Actions cron не гарантує точного часу запуску: зберігати heartbeat і контроль пропусків; якщо потрібна суворіша періодичність, оцінити окремий scheduler за бюджетом і доступними планами.
